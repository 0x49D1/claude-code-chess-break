# AGENTS.md

Notes for coding agents (Claude Code and others) working on chess-break. The user-facing story is in `README.md`. This file covers what the code does not show.

## What this is

chess-break is a Claude Code **mod** (plugin): chess puzzles in a pane while Claude works. It is written in TypeScript/TSX against the mod engine's `claude-code` module. There is no Node, bundler or `package.json`. The engine loads `hooks/register.ts` (see `hooks/hooks.json`).

## Commands

```
claude plugin validate .   # the plugin's shape: manifest, hooks, state (no type check)
npx -p typescript tsc --noEmit -p .   # the type check, against the engine's types
claude plugin test .       # runs tests/*.test.ts
claude --plugin-dir .      # try it for real
```

The engine's types live in `.claude-plugin/types/` (gitignored, written by the engine). Read `.claude-plugin/types/claude-code/index.d.ts` for the API: `$.http`, `$.process`, `$.clock`, `$.store`, `$.ui`, events. Don't guess.

## Engine rules the code must follow

- A file that reads or updates the pane's state declares the `view` atom itself: `atom({ plugin: 'chess-break', key: 'view' } as const, INITIAL_VIEW)`.
- `$` is passed only into `function` declarations, never into arrow functions or object methods across files.
- A mod imports only its own files. That is why chess.js is copied into `hooks/vendor/`.
- `$.http.fetch` returns the whole answer and cannot stream. For streams, use `$.process.spawn` (see the sign-in listener in `hooks/app/account.ts`).

## Layout and where logic goes

- Pure logic (no `$`) lives in `hooks/chess/`, `hooks/training/`, `hooks/lichess/`, `hooks/chesscom/` and `hooks/offline/`. Tests call it directly.
- Anything using `$` (state, network, store) lives in `hooks/app/`. Drawing lives in `hooks/ui/`. Slash commands live in `hooks/commands.ts`.
- All shared types are in `types/index.d.ts`.
- Every user-facing text goes through `hooks/i18n/`. `Messages` is typed, so a new text must be added to `en`, `fr`, `ru` and `ka`, or the type check fails. The Georgian theme names are unreviewed.
- `hooks/offline/puzzles.ts` is generated by `scripts/pick_offline.py`. Don't edit it by hand.

## TypeScript architecture

How the code is written, so that new code fits it. Each rule names a file where it can be seen.

**Layers, and which way imports go.** Each layer imports only from the ones above it in this list, never from below:

```
types/index.d.ts          the data: plain types, no code
hooks/chess, training,    the pure core: never given $, tested directly
  lichess, chesscom,        (training/game.ts: a game's moves and clocks)
  offline, i18n
hooks/app                 actions: the only code that calls $ for network, store, processes
hooks/ui                  drawing: reads the view, calls actions on presses
hooks/commands.ts         a thin router from /chess-break words to actions
hooks/register.ts         wires hooks to the above
```

The core never imports `hooks/app` or `hooks/ui`, and `hooks/app` never imports `hooks/ui`. Logic that needs no `$` goes in the core, even when only one action uses it: `playTyped` in `training/game.ts` is shared by the pane and the prompt, and tested alone.

**State is plain data, changed by copies.**
- The pane's state is one `View` (`types/index.d.ts`), changed only through `update($, view, v => ({ ...v, … }))`.
- Core functions take a value and return a new one: `applyState(game, state, now)` in `training/game.ts`, `play(attempt, text)` in `training/attempt.ts`.
- There are no classes.

**What the pane says is a value, put into words in one place.**
- Outcomes are discriminated unions: `Feedback` and `GameNote` in `types/index.d.ts`.
- Only `hooks/i18n` turns them into text (`note(n)` in `hooks/i18n/en.ts`), with a `switch` the compiler checks for every kind.
- A new outcome is a new kind, never a string built in an action.

**Data from outside is checked where it comes in.**
- JSON from Lichess, Chess.com or the store is read in one function: `readGameEvent` in `lichess/game.ts`, `parsePuzzle` in `lichess/client.ts`, `storedProgress` in `app/state.ts`.
- It is cast to a shape whose fields are all optional, and each field is checked before use.
- Those reads, and `as…` guards after a membership check (`asSource`, `asLocale`), are the only places a cast belongs.
- There is no `any`, and no cast used to quiet the compiler.

**Errors.**
- Parsers may throw: `readAnswer` in `lichess/client.ts`.
- Actions catch, and turn every failure into a value the pane shows: `refusal()` in `app/game.ts` maps a status to a `GameNote`; `loadNext` in `app/actions.ts` falls back to the offline set.
- Nothing thrown reaches `hooks/ui` or a command's answer.

**Module-level mutable state** is only for what cannot live in the view: child processes and timers (`children` in `app/curl.ts`; `followed`, `tick` in `app/game.ts`; `refresher` in `app/games.ts`; `listener` in `app/account.ts`). Each has a comment saying what it holds.

**Background work** started with `void` ends in `.catch(…)`, as in `app/game.ts`, so a promise left running when the module unloads rejects quietly.

**Size.**
- A file past about 300 lines, or a function past about 40, is split along a layer line, not into helpers called once.
- No new dependency: the engine allows only the mod's own files (chess.js is vendored), and a few lines of our own beat a copied library.

**Tests.**
- Core functions are tested directly: `tests/game.test.ts`, `tests/training.test.ts`.
- Actions and drawing are tested through the engine, with `http.fetch` and `process.spawn` stubbed and the pane mounted: `tests/play.test.ts`, `tests/pane.test.ts`.
- A test that leaves a stream or a timer open fails the file, so end them (`endAll()` in `tests/play.test.ts`).

**Done means** all three pass: `npx -p typescript tsc --noEmit -p .`, `claude plugin test .` and `claude plugin validate .`. `validate` checks the plugin's shape, not its types: passing it says nothing about type errors.

**Refuse these:**
- A type guard (`x is T`) on a value already of type `T`: its false branch narrows to `never` (`isOn` in `training/game.ts` takes a `Game` and answers a plain `boolean` for that reason).
- `as` to make an error go away.
- An action that throws to the pane.
- A helper, option or wrapper with one caller and no test.
- A copy of a function with one detail changed: give the original a parameter instead.

## Tests

Tests run with no fs, network or process. Stub them with `on('http.fetch', …)` and `on('process.spawn', …)`, and use `mock.store(on)` / `mock.clock(on)` from `claude-code/testing`. Follow `tests/account.test.ts` and `tests/pane.test.ts`. New non-trivial logic gets a test.

`tests/pane.test.ts` mounts the real pane with `$.ui.mount`, so drawing is tested too, not only logic. An agent cannot see the pane in its own session. To check the real screen, run a second Claude Code in tmux and read it as text:

```
tmux new -d -s cb -x 120 -y 40 'claude --plugin-dir .'
tmux send-keys -t cb '/chess-break' Enter
tmux capture-pane -t cb -p      # -e keeps the colours
```

That second session uses the user's login and the network, so ask first. Browser tools such as agent-browser do not apply, because there is no web page.

## Security and privacy

- The Lichess token stays in `$.store`. It never goes into the conversation, a command argument (`/chess-break login <token>` is refused on purpose), a log, or a process's argv. Pass it on stdin.
- Ask Lichess for the fewest OAuth scopes (`SCOPES` in `hooks/lichess/auth.ts`).

## Style

- Comments are short, say why, and are written in plain sentences. Match the surrounding density.
- Names are plain words (`storedToken`, `loadNext`). The code does not use abbreviations or `I`-prefixed types.
- README and texts use short sentences and no marketing tone.
